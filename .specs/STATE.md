# Project state

## Decisions

| ID | Decision | Rationale | Status | Date |
| --- | --- | --- | --- | --- |
| AD-001 | A calendar date (a day with no time of day) is stored as `YYYY-MM-DD` text, not as an epoch-millisecond timestamp. Timestamps stay for instants such as `createdAt` and `updatedAt` | a transaction date is a day, not a moment: as a timestamp the same bill could fall on another day in another time zone, and month-end rules would depend on whose clock is used. Approved with the Transactions plan ("Ok Agree"), after the explanation of this decision | active | 2026-11-12 |
| AD-002 | Categories are a flat list in the web layer; the category tree (children expanded by default) waits until the Category API has a parent field | the Category API has no parent field and the web layer may not add APIs. Question: "The Category API is flat... How should the 'first level of child categories expanded by default' requirement be handled?" Option chosen: "Flat list now (Recommended)" | active | 2026-11-17 |
| AD-003 | The web page computes the running balance and monthly totals itself: the opening balance of the selected month is 0.00, every occurrence (settled or forecast) counts, and with a category or account filter active they cover only the visible rows | no API returns a balance. Questions: "What is the opening balance...?" Option chosen: "0.00 at month start, all occurrences (Recommended)"; "should the running balance and monthly summary reflect only the filtered transactions or the whole month?" Option chosen: "Filtered transactions only" | superseded by AD-005 | 2026-11-17 |
| AD-004 | The web layer follows the NerdWallet-based `docs/tech/definitions/design.md` (spruce green `#008254`, mint ladder, hairline borders, 2px buttons, 8px cards, Montserrat as the licensed-Gotham substitute with weight 300 body) instead of the Wise-based one; supersedes the Wise tokens named in AC 31 | the author replaced design.md with a NerdWallet version and asked: "Apply it to the current weblayer. The idea will be the same, but the design will change (color, bords, ...)". Layout and behaviour are unchanged | active | 2026-11-17 |
| AD-005 | Balances carry over between months: with no filter or an account filter, the opening balance of a month is the sum of every earlier occurrence (settled or forecast) of the counted accounts, and the Final available balance is that opening plus the month's net; with a category filter (alone or with an account filter) the running balance starts at 0.00 on the month's first day and the four summary totals are hidden. Computed in the API (AD-006). Supersedes AD-003 | the Monthly Balance PRD (`.prd/monthly-balance.md`), confirmed by tghcastro on 2026-11-17: "The Final available balance is the closing balance: the closing balance of the previous month plus this month's net" and "Category filter... the running balance starts at 0.00 on the first day of the month. The summary totals are hidden" | active | 2026-11-18 |
| AD-006 | Business rules that decide what the owner reads - filtering transactions, balances, totals, when a balance carries over or starts at 0.00, when totals are hidden - run in the API (`modules/ledger`); `apps/web` sends the month and the selected filters and only displays what comes back | user, reviewing the Monthly Balance plan: "all business logic should be kept on API. Front-end should only request month and lists to display data. It should not understand when he needs to stop to calculate the acumulative value. Seems that the /transactions/balance would be the best option"; and, asked whether list filters move too, chose "Yes, API filters both (Recommended)" | active | 2026-11-18 |
| AD-007 | Settling an occurrence of a recurring or instalment entry splits it into its own settled one-off transaction and the series skips that date (`transaction_skip`); unsettling leaves a forecast one-off; stopping or shifting a series never touches those one-offs. Existing settlements on series are backfilled the same way | user, reviewing the Monthly Balance plan: "When settling a transaction which was a recurrence, it should (that ocurrence in specific) change to a oneoff and others in next month continue as is"; asked what unsettling does, chose "Stays a one-off (Recommended)" | withdrawn - deferred to a future settle PRD; user: "in caso of no impact im balances we can create a new prd for settle improvement. And implement it in a near future" | 2026-11-18 |
| AD-008 | Identity (users, credentials, sessions, sign-in) is its own module, `modules/identity`, beside `modules/ledger`: same SQLite file, its own migrations folder and Drizzle migrations table, exports only through `index.ts`. The ledger keeps owners as a `userId` text column and never imports the identity module; `apps/api` composes both | identity has its own language and the next three PRDs (user management, password recovery, rate limiting) change it and not the ledger. Approved by tghcastro | active | 2026-11-23 |
| AD-009 | The acting user is the `sub` of a verified `HS256` access JWT sent as `Authorization: Bearer`; the session lives in an `HttpOnly; SameSite=Strict; Path=/auth` refresh cookie `cc_refresh` that rotates on every refresh; the web keeps the access token in memory only. `X-User-Id` is removed. Revoking a session takes effect on other devices when their access token expires | conversation of 2026-11-23 (JWT kept for learning); question "With a pure JWT... Which one?" option chosen: "Accept up to the access token lifetime" | active | 2026-11-23 |
| AD-010 | Client-side routes the API serves `index.html` for are listed explicitly (today `/sign-in`, `/settings/password`); there is no catch-all SPA fallback, so an unknown path still answers `404` | keeps mistyped API paths from answering HTML with `200`; explained to the user when asked whether the APIs stay reachable from outside the container | active | 2026-11-23 |
| AD-011 | When one module must act on another's data, the acting module takes a plain callback at composition (e.g. `createIdentityRouters({ beforeUserDelete })`) and `apps/api` wires it to the other module's exported facade function (e.g. the ledger's `deleteLedgerDataOfUser`); a user's ledger data is deleted before the user, so a retry can always finish | AD-008 forbids the modules importing each other; deleting the user first could leave data nobody can reach or delete. Proposed in the User management plan (2026-11-25) | proposed | 2026-11-25 |
